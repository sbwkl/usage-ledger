## 背景

- 各 AI 编码工具自己把日志 / SQLite 写到本机；这些源会被轮转、迁移、压缩或删除。
- 如果只做“实时读源”，源被删除后历史就永久丢失；如果只做“数据库副本”，又会出现库与源不一致、重复计数、迁移失败等问题。
- 用户需要长期台账、快速聚合，同时要求只读、隐私、无常驻进程。

## 决策

- **源是唯一事实来源**；数据库不承担“权威副本”的角色。
- SQLite 只承担三件事：**抗删除归档**、**聚合索引**、**同步状态**。
- `archived=1` 的明细是数据库唯一不可替代的部分：每日全量重扫推导“源是否还能重建这条记录”，不能重建的标记归档并永久保留。
- 提供 `--stateless` 路径：完全不读 / 不写数据库，直接读源出结果；`report`（读库）与 `--stateless report` 对同一范围必须一致。
- 设计上允许无库实现（`NullStore`）；当前实现是 `SqliteStore` + `--stateless` 无库路径，`NullStore` 类尚未实现。

## 后果

### 收益

- 源可删、库可重建（非归档部分）；不会把数据库当镜像后产生“库里有、源里没有”的假数据。
- `archived=1` 保留源已删除的历史，长期台账成立。
- `--stateless` 提供一致性校验和零落库使用方式。

### 代价 / 后续动作

- 读路径必须维持“读库 ≡ 读源”的一致性约束；新增功能两边都要覆盖。
- `prune` 与 `sync` 的组合需要额外水位 / 区间重算机制；当前存在 P0-1（`prune` 后重放导致 `usage_daily` 重复累计），见 [ARCHITECTURE.md](../../ARCHITECTURE.md) §11。
- `archived=1` 明细当前不压缩，长期体积会增长（P2-1）。

## 替代方案

- **数据库作为权威副本**：拒绝。源被删除时无法判断是“源缺失”还是“数据不存在”，且库损坏 / 迁移失败会永久丢历史。
- **完全不用数据库**：拒绝。无法归档源已删除的记录，也无法做长期聚合与快速查询；`--stateless` 只作为一致性 / 临时使用路径。
- **只保留数据库、不回读源**：拒绝。无法发现源里的新数据，也无法在库损坏时重建。
