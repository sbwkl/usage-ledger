## 背景

- 数据由各 AI 编码工具自己落盘；采集器是“读盘”而不是“接收推送”。
- 用户明确要求极轻量：零常驻内存、无守护进程、默认离线。
- 源日志会被轮转 / 删除，因此需要足够高的采集频率，但不能靠常驻进程实现。

## 决策

- 采用**拉取式采集**：任何时刻读盘都能拿到已落盘的全部数据；不需要订阅流或常驻监听。
- 日常调度使用 launchd：
  - 每小时第 7 分钟增量 `sync`；
  - 每日 00:15 全量重扫 `sync --full`；
  - 每日 00:20 `prune --keep-days 90`。
- `usage live` 直读源，不落库；目标是 `<0.3s` 且无常驻进程。
- 不实现 FSEvents daemon / L3 常驻模式；如未来需要，作为 opt-in 的新 ADR / CHG。

## 后果

### 收益

- 无常驻进程、零常驻内存；安装后不运行也不影响采集（下次运行会补齐已落盘数据）。
- 丢失窗口由“采集间隔 + 源保留期”决定；每小时增量把设计窗口压到约 1h，每日全量兜底。
- 与“源是唯一事实来源”一致：采集器随时可以重建状态。

### 代价 / 后续动作

- 无法看到流式生成中的 in-flight token；`live` 只能显示“上一个已完成 turn”。
- 两次采集之间的源删除仍可能丢数据；`backfill` 只能补仍存在的历史。
- `live` 当前扫描了不需要的 Qoder 轨，实测约 2.3s，未达目标（P1-1）；修复需独立 CHG。
- 调度依赖 macOS launchd；其他平台未支持。

## 替代方案

- **常驻 daemon / FSEvents**：拒绝作为默认。常驻进程不会多拿到任何已落盘数据，反而增加内存、权限与稳定性成本；仅作为未来 <5s 实时的 opt-in。
- **厂商 hook 推送**：只在 Trae CN 用作 token 弱估算（hook 只给字符数），不能替代通用采集；其他源没有等价 hook。
- **每次查询都全量扫描**：拒绝作为默认。Qoder 旧库 + 全部转录可达 GB 级，查询延迟不可接受；保留 `--stateless` 作为显式路径。

## 状态

接受。若未来引入常驻采集，必须新建 ADR，并明确与拉取式的关系（互补或替代）及资源预算。
