# 讨论纪要：从"要不要自研"到"要不要数据库"

> 讨论日期：2026-10-22 ｜ 关联文档：[RESEARCH.md](./RESEARCH.md)（调研）、[DESIGN.md](./DESIGN.md)（方案 v0.4）

本文记录本次讨论的**问题链、关键结论、以及每轮结论对设计文档的修订**，供后续追溯"为什么是这样"。

---

## 需求（原始）

> 我平常使用很多 Coding Agent（opencode、qoder、chatgpt、claude code、kilo、trae CN、workbuddy），桌面版和 cli 都使用。我想知道每个平台、每个模型的 token 使用量。调研互联网上已有的类似产品，判断我应该用开源产品还是自己开发，只考虑 MacOS。

---

## 决策链

### 结论 1 —— 用开源，不自研采集层

调研后给出的判断：采集层**格式漂移是长期维护成本**（厂商随时改 schema），重写不划算；而**报表层没人做得合口味**（各家都在做 UI、社交、宠物、排行榜）。

→ 采纳 ccusage 的准入哲学（无 token 不估算、不爬私有 API），但补上它没有的**归档层**。

### 结论 2 —— "全平台"在数据层就不成立

实测 7 个平台：Qoder（订阅套餐 token **恒为 0**，6898 条）、Trae CN（**只有额度键**）、ChatGPT 桌面端（**无本地数据**）。
→ 明确不采集这 3 个，并在 `doctor` / 报告页脚**显式解释原因**（而不是静默缺失）。理由：静默缺失会被误读成"没花 token"。

### 结论 3 —— 不需要常驻进程

讨论中提出的疑问："如果可以直读 agent 写盘，那是不是就不需要数据库、不需要持续运行？"

拆解后：
- **不需要常驻**：数据是 agent 自己落盘的，采集模型是 **pull**（读盘）而非 **push**（订阅流）。常驻进程不会多拿到任何数据。
- **但需要高频**：实测日志会被归档/迁移/清理（Codex 18 个归档 rollout、OpenCode 双存储、生态自动清理作业）→ **丢失窗口 = 采集间隔 + 日志保留期**。
- → 采集频率由"每日一次"改为 **每小时增量 + 每日全量重扫**，路径显式枚举全覆盖。

### 结论 4 —— 实时性分三档，且 L1 不需要常驻

实测写盘延迟：OpenCode/Kilo **亚秒级**（WAL 直读可见）、Claude Code **turn 结束那一刻**落盘（无中间态记录）。

| 档 | 实现 | 延迟 | 常驻 |
|---|---|---|---|
| **L1** | `usage live` 直读源，不落库 | < 0.3s | ❌ |
| **L2** | launchd `StartInterval=60` | ≤ 60s | ❌ |
| **L3** | daemon + FSEvents | < 5s | ✅（v2 可选） |

**硬边界**：turn 流式生成过程中的 token 爬升在磁盘上不存在 → 任何文件采集方案都看不到，只有 agent 自己的 statusline 才有 in-flight 数值。已写入 R14，避免误解。

### 结论 5 —— DB 是"保险"而不是"镜像"

第二个疑问："既然能直读源，为什么还需要数据库？是不是没用了？"

逐条核算后，DB 的价值只剩四条，且**没有一条是"读现在"**：
1. **抗删除**（源删了只有 DB 有）
2. **抗格式变更**（旧格式解析出的事实已落库；ccusage/tokscale 同样受此影响）
3. **聚合索引**（否则每次扫全盘 ~1.5s）
4. **状态**（水位、告警去重、预算累计）

**架构结论**：**源是唯一事实来源，DB 是可插拔的"归档 + 索引"层。**
- 存储层抽象为同一接口的两个实现：`NullStore`（零 DB、零定时任务）/ `SqliteStore`（归档 + 索引，默认）
- 查询分三档新鲜度：`usage live`（源，实时）/ `usage report --live`（源 ∪ 库，实时）/ `usage report`（库，≤1h）
- **`archived` 标记**（由每日全量重扫推导）区分"源还能重建"与"只有我们留着"——后者永久保留，是 DB 唯一不可替代的部分，也是相对 ccusage/tokscale 的核心差异点
- **锁死正确性**：验收要求 `usage report`（读库）与 `usage --stateless report`（读源）输出**完全一致** → DB 永远只是加速器/保险，不改变答案
